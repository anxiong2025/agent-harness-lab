# Context 上下文压缩

## 一、这条链路要解决什么问题

大模型接口通常是无状态的。每次请求都需要重新发送本轮模型需要看到的内容：系统提示词、工具定义、历史消息、工具调用结果和当前任务。

随着 Agent 执行，上下文会持续增长，最终带来三个问题：

- 超过模型上下文窗口，请求直接失败。
- 输入 Token 增加，单次和累计成本上升。
- 输入变长，首 Token 延迟和总响应延迟上升。

因此，Harness 不能简单地把全部历史无限追加，而要在每次模型请求前重新决定“发送什么”。

## 二、总体链路

```text
组装 Context
    ↓
Token 预算测量
    ↓
Send / Compact / Reject
    ↓
低成本裁剪工具结果
    ↓
结构化摘要
    ↓
摘要事件落盘
    ↓
重新组装 Context
    ↓
请求模型
    ↓
下一轮恢复摘要
    ↓
缓存取舍
```

更简化地说：

```text
Context 预算 → 压缩 → 摘要持久化 → 恢复 → 缓存取舍
```

## 三、每个功能解决什么问题

### 1. Context 预算

解决：不知道当前请求还能发送多少内容，容易直接撞上模型上下文上限。

做法：

```text
可用输入预算 = 模型上下文窗口 - 预留输出 Token - 安全余量
```

每次请求前估算：

```text
system prompt
+ 工具定义
+ 历史摘要
+ 最近消息
+ 工具结果
+ 当前用户问题
```

为什么这样做：模型输出也需要占用上下文窗口，不能把全部窗口都用于输入。

当前代码：

```text
packages/compaction/src/index.ts
  TokenMeter
  BudgetPolicy
```

### 2. 低成本工具结果裁剪

解决：日志、文件、网页和测试输出可能一次性占用大量 Token。

做法：

- 小结果原样保留。
- 大结果保留头部和尾部。
- 去除重复日志。
- 超大结果放到外部存储，上下文只保留引用。

为什么这样做：先用字符串裁剪解决问题，避免一超预算就调用摘要模型，减少额外成本和延迟。

### 3. 上下文压缩

解决：机械裁剪仍然无法把上下文降回安全范围。

做法：保留系统规则、当前任务、关键约束、最近消息、未完成工具调用和重要工具结果，把较早历史转换成摘要。

为什么这样做：不能简单删除历史。删除可能导致模型忘记任务目标、文件路径、错误信息和下一步动作。

工具调用必须成对处理：

```text
assistant tool_call
+ tool tool_result
```

不能只保留其中一条，否则下一次模型请求可能不合法，也无法理解结果对应哪个调用。

当前代码：

```text
packages/compaction/src/index.ts
  CompactionEngine
  BasicCompactionProvider
```

### 4. 结构化摘要

解决：自由文本摘要容易遗漏后续执行所需的关键信息。

摘要应固定包含：

```text
任务目标
关键约束
已完成工作
修改过的文件
执行过的命令
错误信息和测试结果
未完成事项
当前状态
下一步动作
```

为什么这样做：摘要不是给人读的会议纪要，而是给后续 Agent 继续执行任务的状态检查点。

### 5. 摘要持久化

解决：如果摘要只存在内存中，进程重启或下一轮重建时会丢失压缩结果。

做法：把摘要作为事件追加到 Session Log：

```json
{
  "kind": "context_summary",
  "content": "...",
  "coversMessageCount": 42
}
```

原始历史不删除，只是不再默认发送给模型。

为什么这样做：保留原始事件可以支持调试、审计、重放和故障恢复。

当前代码：

```text
packages/session/src/session-log.ts
  latestContextSummary()

packages/core/src/contracts.ts
  context_summary event
```

### 6. 上下文恢复

解决：压缩后下一轮必须继续当前任务，而不是从零开始。

恢复后的模型可见上下文是：

```text
system prompt
+ 历史摘要
+ 最近消息
+ 当前请求
```

为什么这样做：模型不需要看到全部原文，但必须看到足以继续工作的任务状态。

### 7. Provider 超限兜底

解决：本地 Token 估算可能和 Provider 实际计算不一致，尤其是中文、代码、工具 JSON 和不同模型的 Tokenizer。

做法：

```text
Provider 返回 context overflow
    ↓
捕获错误
    ↓
强制压缩
    ↓
重新构建请求
    ↓
限制次数后重试
```

为什么这样做：主动预算负责预防，Provider 错误恢复负责兜底，二者缺一不可。

### 8. 缓存取舍

解决：即使压缩后上下文可发送，稳定内容仍可能被重复处理，造成成本和延迟浪费。

压缩和缓存不是一回事：

```text
压缩：减少需要发送的内容
缓存：避免重复处理相同内容
```

适合缓存：

```text
稳定 system prompt
工具定义
历史摘要
项目索引
短时间内稳定的只读工具结果
```

不适合长期缓存：

```text
实时天气
股票价格
权限信息
动态数据库结果
```

压缩会改变上下文中间的 Token 序列，可能导致 Provider 前缀缓存从变化点之后失效。因此压缩不能过早触发，需要在上下文成本、摘要成本和缓存命中率之间权衡。

先用确定性代码生成摘要结构，确认事件格式和恢复链路；之后再替换为 LLM 摘要 Provider。

在调用摘要模型前先处理大结果，并重新测量 Token。

### 第四步：完善压缩边界 ☑️

确保工具调用和工具结果成对保留，并按任务相关性选择历史范围。

### 第五步：实现 Provider 超限重试 ☐

捕获上下文溢出错误，压缩后重试一次，超过上限则安全失败。

### 第六步：实现基础缓存 ☐

先实现可观察的 Cache Key、TTL 和版本失效，不一开始引入复杂分布式缓存。

```text

```

## 六、最终目标

明天结束时，希望跑通这条真实链路：

```text
长任务
  ↓
多轮模型和工具调用
  ↓
Token 超预算
  ↓
工具结果裁剪
  ↓
结构化摘要
  ↓
摘要事件落盘
  ↓
下一轮恢复
  ↓
任务继续完成
```

核心原则：

> 上下文压缩不是删除聊天记录，而是在有限 Token 预算下，重新构建一份足以让 Agent 继续完成当前任务的上下文。
